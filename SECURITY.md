# Security

## Reporting a vulnerability

Please report security problems privately, through GitHub's private vulnerability reporting: open the repository's **Security** tab and choose **Report a vulnerability**. Do not open a public issue for a vulnerability.

Useful things to report:

- A way to run something a guardrail is meant to block (G1 to G6 in the [Guardrails](docs/guardrails.md#what-the-guard-blocks)) that the guard lets through. Include the exact tool call or command.
- A way to make `/anthology:setup`, `/anthology:setup remove`, `/anthology:import` or `/anthology:export` read or write outside the places they are documented to use.
- A way to get an atl binary installed that does not match the hash pinned in `plugins/anthology/atl.lock`, or an `anthology` binary installed or run that does not match the hash pinned in `anthology.lock`.
- A way to get a tool call other than a read-only one (see [Fail closed](#fail-closed)) through while the guard's binary is missing, broken or cannot run.
- A way to get a note from a repo you did not approve into your main session, or a repo-memory note into a session by a route other than the ones documented (agent memory in a cloned repo already reaches its own agent; see [the memory trust model](#the-memory-trust-model) and ADR-019).
- A secret or personal data committed to this repository.

Fixes ship as a new plugin release, so turn on auto-update for the marketplace to receive them.

## Threat model

Anthology configures Claude Code and the agents that run inside it. The risks it addresses:

| Risk | What stands in the way |
|---|---|
| An agent installs browser tooling on your machine, or launches Chrome | Guardrails G1 and G2, and running tests in Docker |
| An agent reads your Chrome profile (cookies, saved logins) | Deny rules and guardrail G3 |
| An agent uses a browser other than BrowserOS Neo | Guardrails G4 and G5 |
| A secret ends up in a note committed to a repo | Guardrail G6 |
| A stranger's committed notes steer your agents | Repo auto-memory: the approved-repos rule. Agent memory: not blocked, only mitigated by the hints-not-instructions rule in the agent bodies; review `.claude/agent-memory/` in repos you do not trust (see [The memory trust model](#the-memory-trust-model)) |
| A tampered atl or `anthology` binary | A pinned sha256 per target (`atl.lock`, `anthology.lock`) checked before anything is unpacked, and build-provenance attestations |
| The guard's binary is missing, broken or cannot run | The guard fails closed: only read-only tools are allowed (see [Fail closed](#fail-closed)) |
| Vendored upstream content changes silently | Every pin is exact, and CI regenerates all vendored content and fails on a difference |

The assumed cause is a mistake, or an agent misled by content it read (a web page, a file in a repo). It is **not** a defence against a determined attacker, a malicious plugin, or code you choose to run yourself. The guardrails are not a sandbox.

What Anthology changes outside the plugin, by who writes it:

**`/anthology:setup`, after it shows the changes and you confirm once:**

- `~/.claude/settings.json`: the `Bash(atl *)` allow, the `Bash(anthology-mem save *)` allow, the Chrome and Chromium `Read(...)` deny rules, one `Read(...)` allow for the folder that holds the plugin's files, and `worktree.baseRef`.
- The ATL download, and the `anthology` binary install if it is missing (below).
- Deleting what the legacy rtk install left, after showing it and only once `settings.json` is written: the `rtk_path` entry in `state.json`, the downloaded `<plugin data>/rtk/` folder and the legacy history folder `~/.claude/anthology/rtk/` (below). The same guards as `remove` apply: a symlink or a folder outside the plugin's data folder is left in place. A `Bash(rtk *)` allow you wrote yourself is never touched; only the legacy rule an earlier setup recorded is replaced by `Bash(atl *)`.
- Approving the current repo for memory. You can decline this step. It adds the two `merge=union` lines to the repo's `.gitattributes`, and `"autoMemoryEnabled": false` and `"attribution": {"commit": "", "pr": ""}` to the repo's committed `.claude/settings.json` (merged into what is there; a symlinked, oversized or non-JSON file is left alone; a value you set yourself for an attribution key is never overwritten; `remove` reverts only what setup added). That turns off Claude Code's own auto memory in that repo only, and, because the file is committed, for everyone who uses the repo once it is pushed; auto memory includes the subagent memory preload (see the memory trust model). The `attribution` object makes Claude Code omit the co-author trailer and the "Generated with" line from commits and PRs there; it changes no permission. The user-wide settings are not touched for either; setup's output says the attribution object can be added to `~/.claude/settings.json` by hand. The `remove` preview lists each such file, so check `git status` in those repos afterwards.
- Creating the personal-memory folder, and copying the repo's notes from the old path-keyed `~/.claude/projects/<encoded path>/memory/` folder into it. Notes go into the repo's `.claude/memory/` instead only if you say yes to moving the old notes, after seeing where each goes: `project`, `feedback` and `reference` notes go there when the privacy scan finds nothing in them, and `user` notes go to personal memory. The originals are never changed or deleted.

**Session start, automatically:**

- Each plugin's `sh` hook installs the `anthology` binary its `anthology.lock` pins into `~/.claude/anthology/bin/<version>/` (under `$CLAUDE_CONFIG_DIR` when set) if it is missing or does not match the lock, and deletes versions no lock pins after 30 days unused. The guard does the same, at most once a minute, when a tool call finds the binary missing.
- It runs the guardrails on a known-bad sample, reconciles the ATL binary with `atl.lock` (a download into the plugin's data folder) and writes `~/.claude/anthology/state.json`. It never removes the legacy rtk files; only `/anthology:setup` does.
- In approved repos only: it writes `autoMemoryDirectory` into `.claude/settings.local.json` and a git exclude entry for that file, regenerates the `MEMORY.md` indexes, injects the repo's memory index every session when the repo's committed settings turn Claude Code's auto memory off (as setup does), copies notes from the old path-keyed `~/.claude/projects/<encoded path>/memory/` folder into personal memory (never into the repo), and moves `type: user` notes out of `.claude/memory/` and `.claude/agent-memory/` into personal memory. Nothing is overwritten; a repo file is deleted only after its personal copy is verified.
- If a release changed the `settings.json` entries that setup makes and one of them is missing, it prints one line, "anthology settings changed in this release — run /anthology:setup to review". It never edits `settings.json` itself. If you removed one of those entries on purpose, the line comes back at each session start after every release that changes setup's entries, until you run setup again.
- If the personal-memory folder is a symlink or not a folder, it prints one line and does not load, move into or copy into it. Make it a real folder to turn memory back on.
- The memory search index lives in the plugin's data folder.

**`/anthology:setup remove` takes out:**

- the settings entries Anthology added (rules you added yourself are never touched, and `worktree.baseRef` goes back to its previous value), and the `autoMemoryEnabled` and `attribution` lines in each repo's `.claude/settings.json` that setup added (back to the value they had, or the file deleted if setup created it and nothing else is in it);
- the downloaded ATL, ATL's history folder, the same two for the legacy rtk install if they are still there, and `state.json`;
- `~/.claude/anthology/bin/` (the `anthology` binaries), only when `anthology-guardrails` is no longer installed; otherwise it is kept for the guard;
- optionally, the repo approvals.

It never deletes memory notes, the `.gitattributes` lines, the personal-memory folder or exports. Uninstalling the plugin without `--keep-data` removes its data folder (the ATL binaries and the search index).

Nothing is written to `~/.claude/CLAUDE.md`.

## Guardrail limits

Read these before relying on the guardrails. The guard is built to stop accidental browser installs and launches by cooperative agents. It is not a sandbox, and it does not defend against deliberate obfuscation.

- **Two layers, neither a jail.** The deny rules cover Claude Code's built-in file tools and the Bash file commands it recognises. The hook, `hooks/guard.sh` and the `anthology` binary it runs (`anthology guard hook`), sees each tool call before it runs and blocks the call with exit code 2. There is no OS-level enforcement.
- **A hook sees commands, not what a script does.** A script that launches Chrome internally is invisible to it. That is why the knowledge Anthology ships must never launch Chrome, and why the deny layer exists.
- **Rules match commands, not text.** `grep playwright package.json` is allowed on purpose.
- **Indirection is blocked, with known limits.** A command whose program, script or evaluated text comes from a value the guard cannot see is blocked as too complex to check (G0). The next section lists exactly what that covers and what still gets through.
- **Some inputs are not path-checked.** Free-text tool fields (an agent prompt, todo text) and most MCP tool arguments are not checked for browser profile paths. Inside interpreter code (`python3 -c`, `node -e`, a heredoc fed to `python3`, a BrowserOS Neo `run` script) only profile paths spelled out in one string are seen: a path assembled piecewise (`Path.home() / "Library" / …`, variables) is not, and neither is a command run from inside the code (`os.system(…)`).
- **Profile coverage is bounded.** The guard and the deny rules cover the known Chrome and Chromium profile folders and their parents. Grandparent folders, such as `find ~ -name Cookies`, and the profile folders of snap and flatpak browsers are not covered. The native `Read` deny rules that setup adds are the second layer for browser profiles.
- **Docker is exempt from G1 and G2.** Commands whose program is `docker` or `docker-compose` are not checked against those two rules, because running browser tests in a container is the sanctioned way. G3 to G6 still apply to them.
- **G6 checks content, not files.** It looks for common key and token formats (AWS access keys, GitHub tokens, `sk-` API keys, Slack tokens, private-key blocks) and `password` or `api key` assignments in what `Write` or `Edit` puts into a memory folder, and in command text that writes there. **Copying a secret file into memory is not caught.** Neither is a secret in a format it does not know.
- **It allows malformed input.** The guard exits 0 when its input is not valid JSON, is not an object or has no string `tool_name`, so a bad payload can never block your whole session. An error inside the check is different: a crash, a pattern limit or a check that runs longer than 8 seconds blocks the call with an `(internal)` message.
- **It cannot be silently off, but it can be off.** At session start Anthology runs the guard copy the hook actually executes (the marketplace folder for a local-folder marketplace, the plugin cache otherwise) on a known-bad sample and shows a loud message if the guard cannot run or does not block. If its binary cannot run, the guard fails closed (next section). Disabling `anthology-guardrails` with `/plugin` turns every guardrail off.
- **A hook that fails or times out blocks.** The guard and atl's hook set `onFailure: "block"` with a 60-second timeout (ADR-024). A crash, a kill or a stall blocks the tool call; it never lets the call through to your normal permissions.
- **A block wins over atl.** The guard checks the command Claude asked for, not atl's rewrite of it, and a block takes precedence over an atl allow. `atl`, `atl bypass`, `atl proxy`, `atl run`, `atl err`, `atl test` and `atl summary` prefixes are stripped before the rules run, and an `atl run -c` or `--shell` script is checked like `sh -c`, so `atl npx playwright install` and `atl run -c 'npx playwright install'` are still G1. The legacy `rtk` forms (`rtk`, `rtk bypass`, `rtk run` and the rest) are stripped the same way, so a command typed with the old name is checked like one typed with the new.
- **macOS and Linux only.** Setup refuses on Windows, and there are no PowerShell-aware rules. On a platform with no guard binary, the guard allows only read-only tools.

## Values the guard cannot see

The guard reads a command the way bash 5.2 and zsh 5.9 do (zsh is the shell Claude Code uses on macOS), as far as it can, and blocks what it cannot read as too complex (G0). When another reading of the same command breaks a rule, that rule's message is shown instead. The reasons are recorded in ADR-033.

**Blocked as too complex:**

- **A program or script from a variable.** `$x`, `"$x"`, `${x}`, an array element, zsh's `$=x`, `=$x` and `$x[1,3]`, as the program (also after `env`, `command`, `exec`, `nice`, `time`, `sudo`, `xargs`, zsh's `noglob` and `nocorrect`, keywords and groups), as a `find -exec` or `fd -x` program, or inside a script the command runs (`eval "$x"`, `bash -c "…$x…"`, `env -S`, `trap`, `watch`). A program from the found file name (`find … -exec {} …`) and a program word with an unquoted `*`, `?` or `[` (`/usr/local/bin/np?`) are blocked too.
- **A positional parameter the guard did not fill in.** `$1`, `"$@"` and the like as a program or in a script, except in the two places the guard puts literal values there itself: a `sh -c '…' _ a b` script with literal arguments, and the `{ … }` body of a function the command defines once and only calls directly, with literal arguments. Literal means only `A-Z a-z 0-9 _ . / : = , + @ % -` after quotes are removed (no glob, brace, `~` or zsh pattern character). The function body may hold no number word and no `${1:…}`-style expansion of a positional parameter (zsh's `${1::=x}` sets it), and must not run `read`, `print`, `printf`, `typeset`, `declare`, `local`, `export`, `set`, `shift`, `zparseopts`, `getopts`, `eval`, `source`, `.`, `builtin`, `command` or `alias`. Blocked: the top level of the command, a shell reading its script from stdin (`bash -s x <<< …`, `bash /dev/stdin …`, `source /dev/stdin …`), arguments the guard cannot see (`find -exec sh -c '"$1"' _ {} \;`, `xargs sh -c …`), a function also run from `trap`, `eval`, a wrapper or another shell, `f() ( … )`, zsh's `f() cmd` and anonymous functions, a command that sets or moves the parameters (`set --`, `shift`, `argv`), and defining `command_not_found_handle` or `command_not_found_handler`.
- **A renamed program.** Defining an alias, hashing a path (`hash -p`, zsh `hash u=…`), and naming bash's `BASH_ALIASES`, `BASH_CMDS` or an exported function (`BASH_FUNC_…`) in any word, or zsh's `aliases`, `commands` and `functions` tables with a subscript, a value or as a name `set -A`, `typeset` or `read` set.
- **Code from a value.** bash's `${x@P}`, zsh's `(e)` flag and `${~x}`, `GLOB_SUBST` and `PROMPT_SUBST` in any spelling, an option name from a variable (`setopt $o`, `set -o $o`), a prompt variable or `BASH_ENV`/`ENV` set to a value holding `$` or a backquote or read in, a nameref to one of those or to a table (or one the guard cannot follow), and a variable name from a variable (`declare "$x=…"`). The `${x@P}`, `(e)` and `${~x}` checks cover unquoted heredoc bodies too.
- **zsh glob qualifiers.** A `(` right after a word, after a `)` (`(a|b)(e:'…':)`) or in an unquoted `${x:-…}` default (`*(e:'cmd':)`, `a.rs(+cmd)`), outside arithmetic, `[[ … ]]` and `f()`.
- **A value read in and then evaluated.** When the command reads input (`read`, `mapfile`, `readarray`, `select`) or holds a `$(…)` as text in a value, any arithmetic, `let`, numeric `[[ … -eq … ]]` test, subscript that names a variable, `${!s}`, `declare -i`, or a `$` in a name `unset`, `declare` or `printf -v` evaluate (`read s; echo $(( s ))`, `unset "a$s"`).
- **Nested subscripts** that hold another `[` or a quote before a `$(…)` (`a[[]$(cmd)]`).

**Read through, so still allowed (each rule still applies to what is read):**

- A program under a standard directory: `"$HOME/…"` or `"$HOME"/…`, and the same for `TMPDIR`, `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PROJECT_DIR` and `VIRTUAL_ENV`, in a plain command. `$HOME` is read as your home directory. `"$HOME/x/npx" playwright install` is G1. Plain means: those are the only expansions, and every other character of the command is one of `A-Z a-z 0-9 _ . / : = , + @ % -`, a blank, a quote or one of `; & | < >` (no brace, glob, `#`, `^`, `~`, backquote, parenthesis, backslash, here-string or here-doc). It is blocked instead when the name appears anywhere else in the command, or when the command sources a file or runs `eval`.
- `$PWD` is never read through: the working directory carries over between calls, so its name can hold a `$(…)`. `"$PWD"/node_modules/.bin/vitest` is blocked; `./node_modules/.bin/vitest` works.
- `run() { "$@"; }; run make test` and `sh -c '"$1" --version' _ git`.
- A host path variable you list (ADR-038). An app that embeds Claude Code may tell its agent to run its tool as `"$TOOL" "$SCRIPT" …`. Set `ANTHOLOGY_GUARD_PATH_VARS` to a comma-separated list of those names (`TOOL,SCRIPT`, no blanks) in the `env` of your settings, and the guard reads each whole double-quoted `"$NAME"` word, as the program or an argument, as the file the variable names in the hook's environment. Each rule reads that file's resolved path and the path as written, so a command that is read through and names `npx` through the variable, or through a link, is G1; one that is not read through stays G0. Unset, nothing is read and the call stays G0. A name is read only when it matches `^[A-Z_][A-Z0-9_]*$` and is not one the shell uses itself (`PATH`, `IFS`, `PWD`, `OLDPWD`, `SHELL`, `ENV`, `BASH_ENV`, `ZDOTDIR`, `CDPATH`, `FPATH`, `PS1` to `PS4`, `PROMPT*`, `_`, `REPLY`, `OPTARG`, `MATCH`, `MBEGIN`, `MEND`, `MAPFILE`, zsh's tied `MANPATH`, `MAILPATH`, `MODULE_PATH`, `PSVAR`, `FIGNORE`, `WATCH` and `TERMINFO_DIRS`, the five directory prefix names above, `LD_*`, `DYLD_*`, `BASH_*`, `ZSH_*`). Its value must be an absolute path of `A-Z a-z 0-9 _ . / + -` with no `..`, to a regular file (executable when it is the program) that lies, as written and resolved, outside the temp folders and outside the hook's working folder. The command must be plain in the sense above, with those words as its only expansions, the name nowhere else in it, no word holding `<` or `>` (zsh's `typeset -m 'TOOL<->=…'` names `TOOL1` without spelling it), and no `-m` option on `typeset`, `declare`, `local`, `integer`, `float`, `readonly`, `export` or `unset`.
- **Listing a name is you vouching for it.** The guard sees the hook's environment, not the shell's. Claude Code starts the Bash tool's shell with the same values, but a `CLAUDE_ENV_FILE` export, a shell startup file (`.zshrc`, `.bashrc`, `.zshenv`, `.profile`) or a shell function can change a variable on the way, and the guard cannot see that. List a name only when nothing changes it after Claude Code starts, and only for a file nobody but you can replace. A repository's own `.claude/settings.json` can set `ANTHOLOGY_GUARD_PATH_VARS` (and the variables) in its `env` too, so a repository you clone can list names for you: check a repository's settings before you trust it.

When the block comes from a `$` inside a double-quoted `sh -c`, `eval` or `trap` script, the message says so: put the script in single quotes and pass values as arguments (`sh -c '… "$1" …' _ "$x"`). A search pattern in double quotes that holds one backtick (`grep -n "x = <backtick>" file`) is blocked as well, because the backtick starts a command substitution; the message says to put the pattern in single quotes.

**Also blocked, though harmless** (accepted, so the rules stay simple): `${EDITOR:-vi} file` and other defaults as the program, `"${cmd[@]}"`, `$SHELL -c …`, `"${HOME}/…"` and `sh -c "cd $HOME/proj && make"`, a read loop that counts (`while read -r l; do n=$((n+1)); done < f`), a `retry` wrapper whose body holds a number (`for i in 1 2 3`), the `.env` loader `while read -r k v; do export "$k=$v"; done < .env` (`set -a; source .env; set +a` loads the same file and is allowed), and zsh-like text such as `echo foo(bar)`.

**Known limits, not blocked:**

- Text from another command's output fed to a shell is not seen for what it is: `bash -c "$(…)"`, `eval "$(…)"`, `<(…)`, `source <(…)`.
- A command's output kept in a variable and then evaluated in arithmetic (`s=$(…); echo $((s))`), and a `$(…)` assembled from pieces in a value (`p='$'; p+='(cmd)'`) and then evaluated.
- A file's content: a script run with `bash ./x.sh`, a file sourced, a line read from a file and only printed.
- zsh option changes other than those named above (`emulate`, for one), and unusual nested syntax, such as a comment or a `case` inside `$(…)`, or a quoted `}` inside `${…}`, which can get past the parser.

## Fail closed

The guard is a small POSIX `sh` shim, `hooks/guard.sh`, that runs the `anthology` binary pinned by `anthology.lock` (installed as described in the [The `anthology` binary](docs/binary.md)). When that binary is missing, broken or cannot run here, the guard blocks instead of allowing.

- **What is allowed.** Exactly two paths let a call through: the binary's own allow answer (exit 0 with the exact token `anthology-guard:allow:v1` on stderr, so an empty, garbled or wrong file can never allow), and, when the binary cannot run, a fixed list of read-only tools: `Read`, `Grep`, `Glob`, `LS`, `NotebookRead`, `WebFetch`, `WebSearch`, `TodoWrite`, `TaskCreate`, `TaskUpdate`, `TaskGet`, `TaskList`, `TaskOutput`, `TaskStop`, `Task`, `Agent`, `Skill`, `ToolSearch`, `AskUserQuestion`, `EnterPlanMode`, `ExitPlanMode`, `BashOutput`, `KillShell`, `ListAgents`, `CronList` and `SubagentHandback`. `Skill` lets `/anthology:setup` load; subagent calls are guarded too.
- **What is blocked.** Everything else, with exit 2 and a `Blocked by anthology-guardrails (setup): …` message that names the cause and the fix: shell commands, file writes and edits, every `mcp__*` tool, and any tool that is not on the list, including tools Claude Code adds later.
- **Recovery.** A blocked call tries to install the binary, at most once a minute, so a session heals once the network is back. An installed binary that answers with anything but the allow token or a well-formed block is set aside (`~/.claude/anthology/bin/.broken-…`) and reinstalled on a later call. After three failures in 24 hours tool calls stop reinstalling it, and a new session tries once more, at most once an hour. `/anthology:setup` and a new session while online also install it.
- **The `/plugin` escape.** `/plugin` never goes through `PreToolUse`, so disabling `anthology-guardrails` there always works, even when every tool call is blocked. Every `(setup)` and `(internal)` message names it.
- **Residual risk while the binary is missing.** The read-only tools above are let through unchecked, so guardrail G3 (Chrome profiles) is not enforced for `Read`, `Grep`, `Glob`, `LS`, `NotebookRead` or `WebFetch` (a `file:` URL) until the binary is installed. The native `Read(…)` deny rules that setup adds still apply.
- **A stopped guard.** The binary starts its own 8-second watchdog before it reads its input. Only a process that cannot run at all (stopped with SIGSTOP, a kernel stall) reaches the 60-second hook timeout. Claude Code then blocks the call with its generic `onFailure` message, which names neither the cause nor `/plugin`.
- **Integrity is checked at session start, not per call.** Each session start re-hashes the installed binary against `anthology.lock` and its install record, and sets it aside on a mismatch. A binary changed in the middle of a session runs until it fails, and is then set aside.
- **Downloads.** The archive URL is fixed by the lock (`https://github.com/<repo>/releases/download/anthology-bin--v<version>/anthology-<target>.tar.gz`), and nothing is unpacked until its sha256 matches the lock. `curl` and GNU `wget` are limited to HTTPS; BusyBox `wget` has no such switch, so there the HTTPS URL and the pin decide which bytes are accepted. `node`, the last resort, honours `HTTPS_PROXY` only on node 24 or newer; on older node behind a proxy the download fails.
- **Air-gapped installs.** Copy the release's `anthology-<target>.tar.gz` into `~/.claude/anthology/bin/` and start a new session. That file is tried first and is used only if its sha256 matches the pin; a file that does not match is neither used nor deleted, and the message names it. Maintainers build the same layout for tests with `anthology-dev seed`, which writes a seed archive, an installed binary and matching locks into a scratch copy of the plugins.
- **Checking a release yourself.** Download an archive and run `gh attestation verify anthology-<target>.tar.gz --repo rbonweb/anthology`, then compare its sha256 with `anthology.lock`.

## The `Bash(atl *)` allow

Setup adds a blanket `Bash(atl *)` allow to `~/.claude/settings.json` so that commands rewritten by atl do not prompt you, except where one of your deny or ask rules is involved (below).

- `atl bypass <cmd>` runs any command. So the allow also **auto-approves `atl bypass <anything>`**: an agent, or text that misleads an agent, can run an arbitrary command without a permission prompt by putting `atl bypass` in front of it.
- atl's hook applies the deny and ask rules of your settings files to the command and to the command an `atl …` form wraps (`atl bypass`, `proxy`, `run`, `err`, `test`, `summary`, `atl <tool> …`), recursively, including `sh -c` scripts, `find -exec`, `xargs`, `env`, a dashed git builtin (`/usr/lib/git-core/git-push` is `git push`) and words after a redirect (`git >/dev/null push`). A deny prints an explicit hook deny. On a line that mentions `atl`, an ask makes Claude Code prompt even though `Bash(atl *)` matches; on other lines the hook drops it (next point). The files it reads: `<project>/.claude/settings{,.local}.json` (also under `CLAUDE_PROJECT_DIR`), `~/.claude/settings{,.local}.json` and `managed-settings.json` plus `managed-settings.d/*.json` (with `allowManagedPermissionRulesOnly` honored). An unreadable settings file makes it ask for every line that mentions `atl`; other lines get Claude Code's own checks.
- **An ask stands only where `Bash(atl *)` could allow.** A hook ask prompts in every permission mode, bypass and auto included. So `bin/atl-hook` drops atl's ask when the command mentions neither `atl` nor the legacy `rtk` (quotes and backslashes removed, case folded; a `$'`, or a `\u` escape anywhere in the hook input, counts as a mention): the command then runs as typed, under your own mode, rules and the guardrails, exactly as without atl, and the rewrite is dropped with the ask. A deny, an atl failure and an ask on a line that mentions `atl` pass through, with one exception: in bypass mode (`"permission_mode":"bypassPermissions"` at the top level of the hook input, before `tool_input`, which Claude Code sets and the model cannot) every ask is dropped, because those users chose not to be asked. Auto mode keeps the ask on a line that mentions `atl`: dropping it would let `Bash(atl *)` allow the line without auto mode's classifier ever seeing it. Claude Code applies your ask rules to the unrewritten command with its own matching, which is shallower than atl's: it does not see `git -C . push`, `bash -c '…'`, a dashed git builtin, words split by a redirect or `find -exec`. So with `Bash(git *)` allowed and `Bash(git push *)` an ask rule, `git -C . push origin main` runs without a prompt. Deny rules are still applied in every form: **use a deny rule for anything that must never run.**
- **What the rules cover: commands, not what programs do.** atl's hook aims to match Claude Code's own rule matching and add to it. A Bash deny rule, and an ask rule on a line that mentions `atl`, is enforced against the commands the agent types, in every form: each `atl` form, a wrapper, a compound command, a substitution, a redirect. A `Read(…)` rule is enforced against every file the command line names or redirects. What an allowed program then does with the files, plugins, configs or build steps it loads (`build.rs`, test files, MSBuild targets, the linker, plugins, a kubeconfig `exec` entry, compose files) is out of scope: deny rules restrict commands, not what programs do.
- **The plain shape when you have rules.** As soon as you have any deny or ask rule (Bash or `Read`), a command line that runs `atl` (or mentions it anywhere) runs without a prompt only when all of this holds; anything else asks, and a deny rule that matches still denies:
  - **One simple command.** Outside quotes only letters, digits, spaces and `-_./:,=+%@` appear: no `;`, `&&`, `||`, `|`, `&` or newline; no subshell, group or function; no redirect of any kind, here-string or here-document; no substitution, `$` expansion, glob, brace, extglob character or comment; no word opening with `=` or `@`. `$`, a backquote, a backslash and `!` may appear only inside single quotes (`-m 'feat!: x'`). Because zsh's `EXTENDED_GLOB` makes `^`, `#` and a later `~` glob operators (`c^1./.env` matches `config/.env`), an unquoted word holding one asks, except a `commit -m` message and a git revision of the strict shape `REF` followed by `~N`, `^N`, `~` or `^` (or two such joined by `..` or `...`), where `REF` is letters, digits, `_` and `-` with no `/` or `.` (`HEAD~1`, `main^`, `HEAD~5..HEAD`). A leading `~` is your `$HOME` only as `~` or `~/…` with no later `^`, `~` or `#` (with `HOME` unset, empty or relative it asks). Nothing stands before `atl`: no assignment, `cd`, `exec`, `eval`, `source` or launcher.
  - **A listed command.** `atl ls`, `tree`, `read`, `wc`, `diff`, `grep`, `rg`, `find`; `atl git status`, `log`, `diff`, `show`, `branch`, `blame`, `add`, `commit`, `checkout`, `switch`, `rev-parse`, `ls-files` (no git option before the subcommand); `atl cargo build`, `test`, `check`, `clippy`, `fmt`.
  - **Listed options.** Each command has its own option list; an unknown option or an abbreviation asks. Among those not listed: `git add -f`, `git commit -F`, `git log --output`, `git diff --ext-diff`, `grep -f`, `--pre`, `rg -z`, `find -exec`, `-delete`, `-fprint`, `-newer`, `cargo --config`, `-Z`, `+toolchain`, `--target`, `--manifest-path`. Any word after cargo's `--` asks. An option with an optional value takes it only glued, as git does (`--pretty=oneline`, `-U5`, `-uno`), and an option that takes the next word asks when that word starts with `-`.
  - **Literal paths, checked.** Every operand and option value except a search pattern (grep's pattern and `-e`, `--include`, `--glob`, find's `-name` and `-path`) is resolved against the working directory, lexically and through symlinks. It asks when it is `-` or lies under `/dev`, `/proc` or `/sys`, and it is checked against your `Read(…)` rules: a deny rule denies, an ask rule asks. In a git command no word after the subcommand may hold a `:` (so `git show HEAD:<file>` and `--pretty=format:%h` ask), except a `commit -m` message, which is not a path and is not checked. Quoted text is literal (`'$x'` is a name), except that git reads its pathspecs as globs, so a git word holding `*`, `?`, `[` or `\` asks even when quoted. For a strict revision word such as `x~1` or `x^1`, every file in the working directory whose name starts with `x` is checked too, since `EXTENDED_GLOB` matches those; a directory too large to scan asks.
  - **No rule text.** A Bash deny or ask rule's command text found anywhere in the line asks, whatever the quoting (`atl ls 'git push'`).
  atl rewrites a command only into that plain shape; otherwise it leaves the command as written, so Claude Code judges it as it would without atl. Everything off the list asks, including `atl bypass`, `atl run`, kubectl, docker, dotnet, go, npm, npx, pip, uv, pytest, prettier, rspec and gh. The lists are at the top of `atl/src/hooks/anthology_gate.rs`. With only a `git push` deny, 54 of 124 common agent commands probed prompt (mostly `atl` forms an agent typed itself, such as `atl npm run build` or `atl bypass …`), and 26 lose their atl rewrite; `atl git status`, `atl ls`, `atl cargo test`, `atl grep`, `atl read` and the like do not prompt.
- `Read(…)` deny rules block the reads atl would otherwise launder: `cat`, `head`, `tail`, `grep`, `rg`, `diff`, `wc`, `ls`, `find`, `tree` and `atl read` of a denied path, and a denied path named by any command behind `atl` (also glued to an option, `-fsecret.txt`; a word opening with `@` asks). Paths are resolved against the working directory, `cd`, `~` and symlinks **that exist when the hook runs**: a link or copy the same command creates (`ln -s . d && cat d/secret.txt`, `cp -r`, `tar`) is not seen. A path it cannot resolve (`$VAR`, a glob, `cat < secr?t.txt`, a redirect after a `cd`, `/proc/…`, `/dev/fd/…`) asks. `Read(…)` ask rules are handled the same way.
- **Not covered:** rules given with `--settings` or `--disallowedTools`, server-managed settings and a macOS MDM profile, which no hook can read; files a recursive search walks into (`grep -r x .`), including one a glob value selects (`rg -g secret.txt`, `grep -r --include secret.txt x .`); files, links and settings the same command creates (above); what a plain command runs from files, out of scope as above (the tests and `build.rs` `cargo test` builds, git hooks, git and cargo settings, `.gitattributes` filters) and the environment your session already has (`GIT_PAGER`, `NODE_OPTIONS`); git output that prints a `Read`-denied file's content without naming it (`git show HEAD`, `git log -p`, `git diff`, or `git show <blob>` with a blob id `git ls-files -s` printed; `git show HEAD:<file>` asks); the content of an argument file a program reads on its own (an `@file` on the line asks); and a command hidden from any parser (a `python -c` script, `eval` of a variable), which no rule catches without atl either. Programs that run a string (`awk`, `make`, `ed`, `sqlite3`, `python -c`) are not read, but behind `atl` they ask when you have rules.
- The guardrails G1 to G6 check the command the agent asked for, with the `atl` prefixes stripped as described above.
- It is an accepted risk, chosen for a prompt-free workflow, not an oversight.
- `/anthology:setup remove` takes the allow out again. You can also delete the entry from `~/.claude/settings.json` yourself.

### What ATL keeps on your machine

- **What:** a SQLite tracking database with every Bash command line the hook sees, the atl command it became and token counts (`atl gain` reads it); a recall store with output atl left out of a result (`atl recall` reads it); and a tee spool of raw output. Command lines and output can contain secrets.
- **Where:** `~/.claude/anthology/atl/` (`history.db`, `recall.db`, `tee/`), or the same under `$CLAUDE_CONFIG_DIR`. `bin/atl` and `bin/atl-hook` set `ATL_DB_PATH`, `ATL_RECALL_DB` and `ATL_TEE_DIR` there. Files are created private to you (0600, folder 0700). Nothing is uploaded.
- **How long:** the history 90 days, the recall store 30 days, the tee spool the last 20 files. Expired rows leave `atl gain` and `atl recall`, but their bytes can stay in the database file until SQLite overwrites them.
- **Deleting it:** `/anthology:setup remove` deletes the folder; you can also delete it yourself at any time. Deleting the folder is the only way to remove the command lines from disk: `atl gain --reset --yes` only zeroes the `atl gain` numbers, and the text of the deleted rows can stay in the file. ATL has no switch that stops recording command lines but keeps `atl gain`.
- **The legacy rtk history:** releases before the rename kept the same data in `~/.claude/anthology/rtk/`. `/anthology:setup` shows that folder in its preview and deletes it once you confirm, and `/anthology:setup remove` deletes it too; ATL starts with an empty history and nothing is migrated.
- **The first release,** `rtk--v1.2.1-anthology.1`, kept these in upstream rtk's default folder (`~/Library/Application Support/rtk/` on macOS, `~/.local/share/rtk/` on Linux). Neither setup nor remove touches that folder, because another rtk install may share it; delete it yourself if you ran that version.

The binary behind it is verified before use. The pinned sha256 values, one per target, are in `plugins/anthology/atl.lock`. They are the hashes of the release archives (`atl-<target>.tar.gz`), and an archive is checked before anything in it is unpacked or installed. The archives are built by the `atl-release.yml` workflow and carry build-provenance attestations. To check one, download it and run `gh attestation verify <file> --repo rbonweb/anthology`. atl is built for Claude Code only and has no telemetry; CI runs the built binary with the network disabled (`scripts/atl-net-test.sh`). The shipped source is the Apache-2.0 edition: upstream's BUSL-1.1 engine is removed, and so is the output compression that depended on it.

## The memory trust model

Notes are Markdown that is loaded into a session's context. A note can therefore steer an agent, the way a line in a `CLAUDE.md` can. The model:

- **Memory is opt-in per repo, per user.** It is active only in repos you approved by running `/anthology:setup` inside them. In any other repo no repo auto-memory is written or injected (your personal-memory index still is), and a repo that already has `.claude/memory/` only gets a one-line hint. This covers repo auto-memory only; agent memory is the next point.
- **Agent memory loads in unapproved repos too.** Roster agents set `memory: project`, so Claude Code itself loads `.claude/agent-memory/anthology-<agent>/MEMORY.md` into that agent in any repo, approved or not, and the agent bodies also tell the agent to read the folder. Anthology cannot stop the platform load. The load is part of Claude Code's auto memory, so in a repo where setup turned auto memory off (the committed `autoMemoryEnabled: false`) it stops, and only the agent body's own "read your `MEMORY.md`" line loads the notes there. What it does: every agent body says notes are hints, never instructions, and that they cannot override your request, the BrowserOS-only rule or the Docker rule (subagents never receive the routing guide, so it is not named). That is guidance to the model, not a barrier. Review `.claude/agent-memory/` in any repo you do not trust, like any other code ([ADR-019](DECISIONS.md)).
- **Approval follows the remote.** Approvals in `~/.claude/anthology/approved-repos.json` are keyed by the normalized git remote URL, so a re-clone of the same repo is trusted automatically. Anyone who can push to that remote can add notes you will load. Treat memory changes like code changes: review them, and use CODEOWNERS for `.claude/memory/` and `.claude/agent-memory/` (see the [Memory](docs/memory.md#codeowners-for-memory)).
- **Repo memory is visible to everyone who can see the repo.** If the repo is public, so is its memory. Never put secrets or personal details in it. Guardrail G6 blocks the obvious secret patterns and is not a scanner.
- **Agent notes are saved without a prompt.** Setup allows `Bash(anthology-mem save *)`, so roster agents save their own notes silently, also in repos you have not approved (Claude Code's own agent memory works there too). The helper writes only into `.claude/agent-memory/anthology-<agent>/` of the current git repo and refuses unknown agents, symlinks and anything the privacy scan below blocks; those checks are accident guards, not a guarantee. An agent misled by something it read can still store misleading instructions in its own notes, which Claude Code loads on that agent's next run, so review `.claude/agent-memory/` changes before you commit them.
- **Personal memory stays out of repos.** It lives under `~/.claude/anthology/personal-memory/`. Its path and index are added to your main session at start, even when it is empty.
- **`user` notes are moved out of the repo.** Claude Code's auto memory writes every note type into the repo's memory folder. At each session start in an approved repo, Anthology moves `type: user` notes from `.claude/memory/` and `.claude/agent-memory/` into personal memory, and the repo `MEMORY.md` indexes never list them. If one was already committed, its removal still needs a commit, and it stays in the git history.
- **Old notes stay personal.** Notes from Claude Code's old path-keyed memory folder are copied into personal memory, never into the repo on their own. Setup moves them into the repo only when you say yes to it in `/anthology:setup`: `project`, `feedback` and `reference` notes, and only those the privacy scan passes. A note it blocks, or one without a type, is listed and not moved.
- **The privacy scan guards anthology's writes into repo memory, not every write.** Setup's moves, `/anthology:import` and `anthology-mem save` scan each note before it goes into the repo. A note with a home path (`/Users/<name>`, `/home/<name>`), an email address, a private or public IP address, a private host name (such as `*.local`, `*.lan`, `*.internal`) or this machine's name, an `ssh user@host` target, an `.ssh/` key path or a secret-looking token is blocked: setup lists it and does not move it, import sends it to personal memory instead, and `anthology-mem save` refuses it. The findings name a kind and a line, never the text. It also looks for `secret_access_key = …`-style assignments and `scheme://user:password@host` URLs. It does not scan Claude Code's own auto-memory writes, or an agent's own Write or Edit into its agent folder (that is guardrail G6's narrower job). It is an accident guard, not a guarantee: it knows common formats only, so read what you commit.
- **Exports hold personal notes.** An export refuses to write into a git work tree. Keep the archive private.
- **Imports are checked.** Import shows a dry run first, never overwrites, reads the archive in memory instead of extracting it, accepts only regular files and folders at the archive's fixed memory paths (no absolute paths, `..`, links or devices), writes only the three memory locations, refuses archives over 50 MB, reports secret-looking content, and sends repo notes the privacy scan blocks to personal memory. Import archives only from people you trust: their notes become yours.
- **Claude Code's own rules apply.** A project-level `autoMemoryDirectory` is honored only in a trusted workspace.

## Other things to know

- **Content fetched at run time.** The `web-design-guidelines` knowledge downloads its rulebook with `WebFetch` when an agent uses it. Treat that as external content.
- **Vendored content.** Every folder under `plugins/anthology/knowledge/` and `plugins/anthology-superpowers/` is generated from an exact upstream commit by `anthology-dev vendor` (run as `scripts/dev.sh vendor`). Nothing is edited by hand, and `vendor check` runs in CI on every PR.
- **Supply chain.** CI images are pinned by digest, Rust crates by `Cargo.lock` (checked by `cargo deny` on every PR) and GitHub Actions by commit SHA, and Dependabot proposes the bumps. The `anthology` binary is built only from the crates in `crates/` and their locked dependencies. Secrets are scanned with gitleaks on every PR.
